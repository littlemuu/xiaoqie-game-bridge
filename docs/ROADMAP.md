# 路线：先完成一个能操作真实游戏的闭环

更新：2026-09-16。基于 `main@1f26891`；用户本次已授权直接实现下一阶段并推进第一个可用版本。

## 本次决定

阶段 A（Adapter Contract v2）已经完成。本次将原 B/C/D 的必要部分放进同一个 Minecraft 展示台实现：持久 intent/result → 真实窄观察 → 一个带版本和对账的写动作。阶段顺序作为验证顺序保留，不再把“只读完成”或“基础设施完成”当作本轮终点。

首版固定使用 Minecraft Java 1.20.4、本地专用服务器、RCON 与受信数据包。原 Windows mock worker 不适合直接连接真实游戏，因此新增独立的 Minecraft 入口，继续经过同一个 `GameBridge` 核心；不把网络 adapter 偷换进原 contained mock worker。

## 首版完成门槛

1. 本地初始化专用测试世界，用户自行确认 EULA；服务仅在 loopback 运行。
2. Java 1.20.4 客户端能看到展示台，bridge 能观察其颜色和版本。
3. 本地启用后，预览并确认一个颜色，实际方块改变；返回真实验证结果。
4. `npm run minecraft -- verify` 全部通过；保留实际结果，不以协议夹具替代。
5. 新 MCP 入口接入用户实际客户端后，恰好一个工具可发现；能观察并完成同样的动作，stop 后无新写入。

本轮不声称已完成未执行的第 1–5 项真机检查。

## 保留的边界

- `GameBridge` 继续裁决 session owner、policy、capability、版本、预算和 safety。
- 模型不能提交主机、端口、文件、命令或 resume；配置是本地受信设置。
- 真实入口每次启动 stopped；显式本地操作才启用。
- 结果未知后不重试，先对账；同一世界保留完整、有界的动作记录。
- SQLite 动作记录与普通审计分开；首版的普通诊断是内存环形记录。原 mock durable ledger 不改。
- 游戏保存文件不具备已证明的跨文件原子性；发现历史或方块分歧就拒绝写，不掩盖为“已回滚”。

先根据实际试玩决定第二个值得加入的动作：例如有限移动或小型多方块展示，不预设复杂建筑、战斗或整套游戏控制。每个动作仍须有窄输入、明确权限、版本与恢复证据。
